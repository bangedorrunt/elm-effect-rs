# Harel statecharts with elm-effect-xstate

This guide explains how to model complex state transitions using Harel statecharts and compile them into pure Elm loop folds with `elm-effect-xstate`.

Statecharts extend finite state machines with:
- **Hierarchical (compound) states**: Child states inherit and bubble unhandled events to parent states.
- **Parallel (orthogonal) regions**: A parallel state activates every child region at once, and one event reaches all of them.
- **History states**: Shallow and deep history remember where an interrupted compound state was, and restore it on re-entry.
- **Delayed transitions (`after`)**: The engine arms a timer intent; the host owns the clock and the intent is data.
- **Extended context**: Pure data updated deterministically alongside discrete state.
- **Deterministic action sequence**: State exit actions, transition actions, and target entry actions run in strict topological order (Law L1).
- **Eventless (transient) micro-steps**: Transient transitions (`always`) cascade sequentially until the state machine settles in quiescence (Law L2).
- **Unified action enqueue**: Actions enqueue commands (`exec`), internal events (`raise`), telemetry emissions (`emit`), or actor work (`spawn`, `send_to`, `stop`) via [`ActionQueue`](file:///Users/bangedorrunt/workspace/elm-effect-rs/crates/elm-effect-xstate/src/action.rs), replacing legacy action creators.
- **Pure Elm fold compilation**: The entire statechart compiles down to a deterministic `Program::update` function with zero background scheduler.

## Define states and machine

A machine requires a state key type (implementing `Ord + Clone`), an event type, an extended context type, and a command type:

```rust
use elm_effect_xstate::prelude::*;

#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash)]
enum TrafficLightState {
    Green,
    Yellow,
    Red,
}

#[derive(Debug, Clone)]
enum TrafficLightEvent {
    Timer,
}

#[derive(Debug, Clone, Default)]
struct LightContext {
    cycles: u32,
}

let machine: Machine<TrafficLightState, TrafficLightEvent, LightContext, ()> =
    Machine::builder(TrafficLightState::Green, LightContext::default())
        .state(TrafficLightState::Green, |node| {
            let to_yellow = node
                .transition(TrafficLightState::Yellow)
                .on(|e| matches!(e, TrafficLightEvent::Timer));
            node.on(to_yellow)
        })
        .state(TrafficLightState::Yellow, |node| {
            let to_red = node
                .transition(TrafficLightState::Red)
                .on(|e| matches!(e, TrafficLightEvent::Timer));
            node.on(to_red)
        })
        .state(TrafficLightState::Red, |node| {
            let to_green = node
                .transition(TrafficLightState::Green)
                .on(|e| matches!(e, TrafficLightEvent::Timer))
                .assign(|ctx, _| ctx.cycles += 1);
            node.on(to_green)
        })
        .build();
```

## Start the machine and step it

`Machine::enter` is the start edge: it runs the entry actions of every state it enters and arms their `after` delays. `Machine::step_state` takes the whole run state, so recorded history survives between events:

```rust
let started = machine.enter(&LightContext::default());
let state = MachineState::new(started.configuration, started.context);
let outcome = machine.step_state(&state, &TrafficLightEvent::Timer);
assert_eq!(outcome.current_state, TrafficLightState::Yellow);
assert!(outcome.transitioned);
```

`machine.step(&LightState::Green, &ctx, &event)` is the short form for a chart with one region and no history.

A `Configuration` is the set of active leaf states. `outcome.configuration.leaves()` lists them in a stable order. `outcome.current_state` is the first leaf, which is the whole answer when a chart has one region.

`MachineState` carries three fields: the active `configuration`, the `history` each history node remembers, and the extended `context`.

## Parallel regions

A parallel node enters every child region. Each region keeps its own active leaf, and one event is offered to every region:

```rust
let machine = Machine::builder(Region::Root, ())
    .parallel(Region::Root, |node| node)
    .compound(Region::Left, Region::LeftIdle, |node| node.with_parent(Region::Root))
    .state(Region::LeftIdle, |node| {
        let busy = node
            .transition(Region::LeftBusy)
            .on(|e| matches!(e, Signal::Work));
        node.with_parent(Region::Left).on(busy)
    })
    .state(Region::LeftBusy, |node| node.with_parent(Region::Left))
    .compound(Region::Right, Region::RightReady, |node| node.with_parent(Region::Root))
    .state(Region::RightReady, |node| node.with_parent(Region::Right))
    .build();

let started = machine.enter(&());
assert_eq!(
    started.configuration.leaves().copied().collect::<Vec<_>>(),
    [Region::LeftIdle, Region::RightReady]
);

// One event advances each region that handles it, and leaves the others alone.
let next = machine.step(&Region::Root, &(), &Signal::Work);
assert_eq!(
    next.configuration.leaves().copied().collect::<Vec<_>>(),
    [Region::LeftBusy, Region::RightReady]
);
```

A selection on a shared ancestor is taken once. When a deeper state and an ancestor both select for the same event, the deeper state wins.

## History states

A history node remembers the configuration its parent had when the parent was exited. Shallow history restores the immediate child and resolves its initial; deep history restores the exact leaf:

```rust
let machine = Machine::builder(Spot::Root, ())
    .compound(Spot::Root, Spot::Active, |node| {
        let stop = node.transition(Spot::Stopped).on(|e| matches!(e, Signal::Stop));
        node.on(stop)
    })
    .compound(Spot::Active, Spot::Idle, |node| node.with_parent(Spot::Root))
    .state(Spot::Idle, |node| {
        let play = node.transition(Spot::Paused).on(|e| matches!(e, Signal::Play));
        node.with_parent(Spot::Active).on(play)
    })
    .state(Spot::Paused, |node| node.with_parent(Spot::Active))
    .state(Spot::Stopped, |node| {
        let resume = node.transition(Spot::Deep).on(|e| matches!(e, Signal::Resume));
        node.on(resume)
    })
    // fallback is Idle when nothing is remembered
    .deep_history(Spot::Deep, Spot::Idle, |node| node.with_parent(Spot::Root))
    .build();
```

`.history(id, fallback, ...)` is the shallow form. A history node that has no record enters its fallback.

## Delayed transitions

The engine does not read a clock. Entering a state that declares `after` returns a `TimerIntent::Start`; leaving it returns `TimerIntent::Cancel`. The host schedules the delay and calls `step_timer` when it elapses:

```rust
let machine = Machine::builder(Phase::Idle, ())
    .state(Phase::Idle, |node| {
        let start = node.transition(Phase::Waiting).on(|e| matches!(e, Signal::Start));
        node.on(start)
    })
    .state(Phase::Waiting, |node| {
        let timeout = node.transition(Phase::TimedOut);
        let cancel = node.transition(Phase::Idle).on(|e| matches!(e, Signal::Cancel));
        node.after(Duration::from_millis(500), timeout).on(cancel)
    })
    .state(Phase::TimedOut, |node| node)
    .build();

let started = machine.step(&Phase::Idle, &(), &Signal::Start);
assert_eq!(started.state(), Some(&Phase::Waiting));
assert!(matches!(started.timers[0], TimerIntent::Start { .. }));

let fired = machine.step_timer(
    &MachineState::new(started.configuration, started.context),
    &TimerFired::new(Phase::Waiting, Duration::from_millis(500)),
    &Signal::Start,
);
assert_eq!(fired.state(), Some(&Phase::TimedOut));
```

A timer that fires for a state that is no longer active does nothing, so cancelling a delay without reaching the state is safe. In an Elm program, implement `StatechartDefinition::timer_cmd` to turn an intent into a command the host can run, and have the delay message map back through `extract_event`. The default `timer_cmd` returns `None`, which is correct for a chart with no `after`.

A schema `after` key may name an entry in `delays` instead of spelling milliseconds. `DynamicMachineBuilder::delay(name, resolver)` registers a function that recomputes the duration from context and the event that entered the state; a `None` answer leaves that delay unarmed. `DynamicMachine::enter` supplies the `xstate.init` event. The resolved duration is stored in `MachineState`, so a later context change cannot retarget a fired timer. `MachineState` serializes its armed timers, so `ActorSystem::resume` restores the entry-time duration even when the delay depended on the entry event; no replay is needed. `Machine::timers_for_state` returns those armed starts. Actor timers are available through `ActorSystem::take_timers` and fire through `ActorSystem::fire_timer`.

## Completion

A compound state completes when its child reaches a final state. A parallel state completes when every region does. `on_done` takes the completion transition, and `outcome.done` reports a completed root. Root entry actions run before the initial state's entry; reaching done exits the final state, every active ancestor, and the root exit actions once, without clearing the final snapshot. A JSON machine may declare `"type": "parallel"` at the root, making every top-level state a concurrent region:

```rust
let machine = Machine::builder(Task::Work, ())
    .compound(Task::Work, Task::StepOne, |node| {
        let finished = node.transition(Task::Finished);
        node.on_done(finished)
    })
    .state(Task::StepOne, |node| {
        let finish = node.transition(Task::StepDone).on(|e| matches!(e, Signal::Finish));
        node.with_parent(Task::Work).on(finish)
    })
    .final_state(Task::StepDone, |node| node.with_parent(Task::Work))
    .state(Task::Finished, |node| node)
    .build();
```

## Actors

An `ActorSystem` runs a tree of machine and reducer actors in one process, with no second runtime. It is still pure: `run` delivers queued events, applies the directives actions produced, and returns.

```rust
let root = DynamicMachine::builder(root_config)
    .action("spawn_worker", |_context, _event, enq| {
        enq.spawn("worker", ActorLogic::from_machine(worker_machine()));
    })
    .build();

let mut system = ActorSystem::new("root", ActorLogic::from_machine(root));
system.run()?;                                    // applies the spawn directive

system.send("root", DynamicEvent::new("START"))?;
system.run()?;                                    // walks parent and child
```

Actions on a schema-driven chart reach the actor system through `ActionQueue`:

- `enq.spawn(id, logic)` creates a child of the sending actor.
- `enq.send_to(target, event)` queues an event for another actor.
- `enq.stop(id)` stops an actor and its descendants.

`ActorLogic::from_transition(initial, reduce)` is the reducer form. `ActorSystem::state`, `configuration`, `context`, and `value` inspect an actor without stepping it.

A state can instead own an invoked actor. `"invoke": {"id": "worker", "src": "worker"}` spawns the logic registered with `DynamicMachineBuilder::actor("worker", logic)` on entry and stops it on exit. `onDone` and `onError` are ordinary transition rules attached to that child id. A reentering transition restarts the invoke; a transition that keeps the state active leaves it running.

`invoke.input` is passed to the child at spawn. A literal JSON value works directly; `DynamicMachineBuilder::invoke_input(id, resolver)` computes it from the owner's context and the entry event. Effect, promise, callback, and reducer actors consume it through `from_effect_with_input`, `from_promise_with_input`, `from_callback_with_input`, and `from_transition_with_input`. An invoked machine receives it in the `xstate.init` event, and uses it as initial context data when the machine declares no context of its own.

Completion output travels in the done event. Declare `output` on a top-level final state, or a root `output`, or register `DynamicMachineBuilder::output(state, resolver)` / `root_output(resolver)`. The parent's `onDone` action reads the child output from `event.payload`.

A child that reaches a final state sends `xstate.done.actor.<id>` to its parent, so a parent chart declares that event like any other transition:

```json
{"initial":"Waiting","states":{
  "Waiting":{"on":{"xstate.done.actor.worker":"Finished"}},
  "Finished":{}
}}
```

### Lifetimes

Every actor owns a `Scope` forked from its parent's. `stop` closes the descendant scopes deepest-first; each close interrupts its members and runs finalizers last-in-first-out. `on_stop(id, f)` registers one. `ActorSystem::defects` returns finalizer failures instead of dropping them.

`run` refuses to wait forever: it stops at its step budget and returns `ActorError::StepBudget`, which turns a directive cycle into an error instead of a hang.

Actor verbs exist on `ActionQueue<CMD, DynamicEvent>`; a typed chart keeps its own event type and does not use them. A completed machine actor sends its done event once, even if it receives later events in its final configuration. Timer intents from machine actors are collected with `ActorSystem::take_timers` and delivered back with `ActorSystem::fire_timer`; resuming a snapshot keeps the duration armed at entry.

### Host-run actors

`ActorLogic::from_effect` and `from_promise` produce one-shot tasks. Their `_with_input` forms build the task from invoke input. `from_stream` forwards each received value to the parent, and `from_callback` invokes a handler once at spawn with a `CallbackSender`; `from_callback_with_input` also receives the input. These actors keep their lifetime in the system and their work at the host edge:

```rust
for task in system.take_tasks() {
    match Runtime::run(task.effect) {
        Exit::Success(event) => {
            system.complete(&task.actor, event.payload)?;
        }
        Exit::Failure(_) => {
            system.fail(&task.actor, "effect failed")?;
        }
    }
}
```

`system.scope(&task.actor)` returns the actor's `Scope`. Run host work inside it, so `stop` interrupts the fiber and runs finalizers LIFO. `from_promise` has the same completion contract as `from_effect`: this carrier has no separate `Future`, so an `Effect` is the async description a promise resolves to.

## Compound states and bubbling

Compound states contain nested child states. When a child state receives an event it does not handle, the statechart bubbles the event up the ancestry path to the parent:

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash)]
enum PlayerState {
    Active,
    Idle,
    Playing,
    Paused,
    Stopped,
}

let machine = Machine::builder(PlayerState::Active, ())
    .compound(PlayerState::Active, PlayerState::Idle, |node| {
        let to_stopped = node
            .transition(PlayerState::Stopped)
            .on(|e| matches!(e, PlayerEvent::Stop));
        node.on(to_stopped)
    })
    .state(PlayerState::Idle, |node| {
        let to_playing = node
            .transition(PlayerState::Playing)
            .on(|e| matches!(e, PlayerEvent::Play));
        node.with_parent(PlayerState::Active).on(to_playing)
    })
    .state(PlayerState::Playing, |node| {
        let to_paused = node
            .transition(PlayerState::Paused)
            .on(|e| matches!(e, PlayerEvent::Pause));
        node.with_parent(PlayerState::Active).on(to_paused)
    })
    .state(PlayerState::Paused, |node| {
        node.with_parent(PlayerState::Active)
    })
    .final_state(PlayerState::Stopped, |node| node)
    .build();
```

When in `Playing`, sending `PlayerEvent::Stop` bubbles to parent `Active`, exiting `Playing` then `Active` before entering `Stopped`.

## Guards, Actions, and ActionQueue

Transitions support conditional guards and unified action execution:

```rust
let transition = node
    .transition(TargetState)
    .on(|e| matches!(e, Event::Submit))
    .guard(|ctx, e| ctx.is_valid())
    .assign(|ctx, e| ctx.update_from(e))
    .action(|ctx, e, enq| {
        enq.exec(AppCmd::PersistData);
        enq.emit("audit:form_submitted");
    });
```

- `assign(|ctx, e| ...)`: Mutates extended context directly.
- `action(|ctx, e, enq| ...)`: Receives mutable context, the event, and the [`ActionQueue`](file:///Users/bangedorrunt/workspace/elm-effect-rs/crates/elm-effect-xstate/src/action.rs).
- `exec(cmd)`: Convenience helper for emitting a runtime command.

A target whose state is the source defaults to a non-reentering self-transition in XState v6: the transition actions run, but the source's exit and entry actions do not. Add `.reenter()` to exit and re-enter the source, or `"reenter": true` in a schema. A transition to a descendant keeps the source active unless it reenters.

A targetless transition runs its actions without exiting or entering any state. Build it with `node.targetless()`:

```rust
let audit = node
    .targetless()
    .on(|e| matches!(e, Event::Audit))
    .action(|ctx, _, _| ctx.audited += 1);
node.on(audit)
```

In a schema, omit `target`; the transition still runs its guards and actions:

```json
"Active": { "on": { "AUDIT": { "actions": ["record_audit"] } } }
```

Targetless transitions do not add an edge to Mermaid or TLA+ output because they do not change the active configuration.

## Transient Eventless Microsteps (`always`)

Eventless transitions evaluate immediately upon entering a state:

```rust
node.state(LoopState::Counting, |node| {
    let loop_step = node
        .transition(LoopState::Counting)
        .guard(|ctx, _| ctx.count < 3)
        .assign(|ctx, _| ctx.count += 1);

    let to_done = node
        .transition(LoopState::Done)
        .guard(|ctx, _| ctx.count >= 3);

    node.always(loop_step).always(to_done)
})
```

The engine cascades these micro-steps until reaching quiescence (or a safe iteration bound of 100), all within a single `machine.step` invocation.

## Diagrams and durable records

`Machine::to_mermaid` prints a `stateDiagram-v2` with nested blocks for compound and parallel states. `Machine::to_tla()` renders a topology-only TLA+ module (`States`, `Init`, `Next`); guards are Rust closures, so every edge is modelled as enabled; `scripts/verify-formal.sh` generates a module from `examples/emit_tla.rs` and model-checks it with TLC. Set `Transition::label` when the edge name matters, because an event matcher is a closure and carries no name:

```rust
let diagram = machine.to_mermaid();
```

`TransitionRecord` turns one step into a journal entry. Append it before the entry actions run, so a crash replays the transition rather than part of its effects. `TransitionRecord::replay` walks a continuous record chain back to a configuration and never runs actions, so replaying does not repeat side effects. Attach run state with `.with_snapshot(serde_json::to_string(&state)?)`; `ActorSystem::resume(root, machine, state)` restores it without re-running the active states' entry actions. `ActorSystem::snapshot()` serializes the whole actor tree, including host-actor spawn input, and `ActorSystem::restore(snapshot, resolve)` rebuilds every actor with its parent links and armed timers. Restoring a host-driven actor reattaches it: effects and promises re-emit a task, callbacks run again, and streams reconnect to the receiver supplied by `resolve`. Treat this as at-least-once; use a journal when an effect must not repeat.

```rust
let before = machine.initial_configuration();
let outcome = machine.step(&TrafficLightState::Green, &LightContext::default(), &TrafficLightEvent::Timer);
let record = TransitionRecord::from_outcome(&before, &outcome, "TIMER", generation);
record.append(
    &log,
    TransitionStamp {
        producer_id: "traffic-light",
        epoch: 0,
        seq: 4,
    },
)?;
```

## Elm loop integration

To run a statechart inside an Elm `Program`, implement `StatechartDefinition` and wrap it with `StatechartProgram`. A definition whose chart declares `after` also implements `timer_cmd`:

```rust
use elm_effect_elm::{Boot, Cmd, Failure, Program};
use elm_effect_xstate::prelude::*;

struct MyDef;

impl StatechartDefinition for MyDef {
    type State = TrafficLightState;
    type Event = TrafficLightEvent;
    type Context = LightContext;
    type Cmd = AppCmd;
    type Msg = AppMsg;
    type Err = String;

    fn machine() -> Machine<Self::State, Self::Event, Self::Context, Self::Cmd> {
        // Build machine here
    }

    fn init_event() -> Self::Event {
        TrafficLightEvent::Init
    }

    fn extract_event(msg: &Self::Msg) -> Option<Self::Event> {
        match msg {
            AppMsg::TimerTick => Some(TrafficLightEvent::Timer),
            _ => None,
        }
    }

    fn failure(_failure: &Failure<Self::Err>) -> Self::Msg {
        AppMsg::Failed
    }
}

type MyProgram = StatechartProgram<MyDef>;
```

The resulting `MyProgram` satisfies the `Program` trait and can be booted directly in an [`elm_effect_elm::Loop`](file:///Users/bangedorrunt/workspace/elm-effect-rs/crates/elm-effect-elm/src/lib.rs).

## Schema-driven dynamic statecharts and conformance

For CMS-driven workflows or validating behavior against XState JSON specifications, use `DynamicMachine`:

```rust
use elm_effect_xstate::prelude::*;

let json_spec = r#"{
    "initial": "Green",
    "states": {
        "Green": { "on": { "TIMER": "Yellow" } },
        "Yellow": { "on": { "TIMER": "Red" } },
        "Red": { "on": { "TIMER": "Green" } }
    }
}"#;

let machine = DynamicMachine::from_json_str(json_spec)?;
let outcome = machine.step("Green", machine.initial_context(), &DynamicEvent::new("TIMER"));
assert_eq!(outcome.current_state, "Yellow");
```

Behavioral conformance vectors live in `crates/elm-effect-xstate/tests/conformance/fixtures/*.json`: 146 cases across actions, always, after, parallel, history, hierarchy, guards, final states, events, and actors, including ninety-two ported from XState 6.0.0-beta.1 (commit d56483f) whose `source` field names the upstream test. `tests/conformance_actors.rs` runs the actor scenarios (`spawn:`, `send:`, `stop:`, and `assign_payload:` actions, `fail` steps, declarative dynamic invoke inputs, plus invoke input/output/error routes and context assertions); `tests/conformance_test.rs` runs the machine suite and enforces a feature matrix naming the cases that prove each behavior. Run both with `cargo test -p elm-effect-xstate --test conformance_test --test conformance_actors` or `scripts/sync-xstate-conformance.sh`. This is a crate-authored matrix with ninety-two upstream-derived vectors, not a vendored copy of the ~400-case suite. An optional Node check (`scripts/xstate-differential`, `npm run check`) compares final state, `done`, and context against XState for 119 vectors (118 agree, 1 skipped); it is not part of the cargo gate.

## Formal verification (TLA+ / TLC)

In addition to test fixtures, `elm-effect-xstate` is verified against four mathematical state machine models in TLA+ under [`scripts/verify-formal.sh`](../../scripts/verify-formal.sh), documented in [`docs/research/state-machines-and-flows.md`](../research/state-machines-and-flows.md):

- **Flow 6 (`flow6_statechart_microstep.tla`)**: Statechart microstep quiescence, LCA resolution, and Law L1 ordering. Proves `QuiescenceReached`, `StrictOrderExitedBeforeEntered`, and `ValidActiveConfiguration`.
- **Flow 7 (`flow7_statechart_parallel.tla`)**: Parallel orthogonal regions and synchronized join. Proves `OrthogonalIsolation`, `SynchronizedJoinOnDone`, and `NoPrematureCompletion`.
- **Flow 8 (`flow8_statechart_actor.tla`)**: Actor supervision, FIFO mailbox delivery, and recursive scope teardown. Proves `NoLeakedChildrenOnParentExit` and `FinalizersSettledBeforeClosed`.
- **Flow 9 (`flow9_statechart_timer.tla`)**: Delayed transitions (`after`) and preemptive timer invalidation. Proves `TimerInvalidatedOnEarlyExit` and `NoStaleTimerWakeup`.

Run all 11 formal verification models anytime with:

