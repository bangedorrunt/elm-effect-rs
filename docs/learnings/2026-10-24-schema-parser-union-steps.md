# A two-phase resolver cannot hand a refused step back

The effect parser resolves steps first and decodes second. The second phase
marks every step "already answered", so a step-carrying node returns its input
unchanged there. That is exactly right when the step ran, and silently wrong
when it did not.

## The trap

A union walk that tries members in order and skips a member whose step refused
looks finished: the next candidate gets its turn. But if no candidate takes the
input and the walk returns the input untouched, the second phase decodes it with
the refused step passed through. `{kind: "b", value: "value"}` came back as a
success where the pin reports a failure (`SchemaParser.test.ts:951`).

The rule: after a step has run or refused, the input may only travel forward if
a member accepted it. Otherwise the refusal is the answer. The second phase
cannot tell a resolved step from a refused one, so nothing that refused may
reach it.

The same reasoning closes the other hole: a step that succeeded but whose
member then refused the answer must not leave the ORIGINAL input to be decoded
in phase two either, because the step would be skipped and the pre-step value
returned. Record the member's own refusal and report that.

## The scheduler

A product fans out; a union cannot. Selecting a member IS the sequential
dependency, so `concurrency: unbounded` changes nothing about a union: the
second member never starts while the first is pending, and never starts at all
once one has answered (`:272`). Any implementation that fans a union's members
out has changed the semantics, not the scheduling.

Constructor defaults are the mirror case: they belong to the construction walk,
not the decode walk, so they need their own entry point (`make_effect`) that
fills the absent keys under the same limit before the synchronous builder runs.
The sync `make` still has to refuse (leave the key absent): it has nothing to
wait with.

## The commit guard

`toron`'s strict guard covers generated artifacts too. `conformance/witness-audit.tsv`
is regenerated by the audit and is not in `docs/learnings/**`, so a beads chore
commit that carries it is blocked as `unreserved` until that path is reserved.
Reserve it with the bead whose rows moved, not with the chore.
